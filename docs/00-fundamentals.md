# Этап 0. Фундамент: как это вообще устроено

Этот документ — не задачи, а объяснения. Цель: чтобы дальше в плане не было слов, за которыми пустота.
Читай по разделам, возвращайся сюда как в справочник.

---

## 1. Как выглядит система целиком

Снаружи есть один вход — `api-gateway`. Браузер или мобилка говорят с ним по обычному HTTP/JSON. Больше никто из внешнего мира внутрь не ходит.

Внутри — набор отдельных процессов (сервисов). Каждый:

- живёт в своём контейнере, у него свой `main`, свой конфиг, свой порт;
- имеет свою базу данных (или свою схему), в которую никто другой не залезает;
- общается с другими только по gRPC (синхронно, «спросил — жду ответ») или через Kafka (асинхронно, «отправил событие и забыл»).

Схематично: клиент → gateway → (gRPC) → сервисы → каждый в свой Postgres. Плюс Kafka сбоку, куда сервисы кладут события и откуда их читают другие сервисы. Плюс Redis как кэш перед базами. Плюс слой наблюдения (Prometheus/Jaeger), в который все сервисы одинаково рассказывают о себе.

**Зачем вообще микросервисы в пет-проекте?** Не ради «модно». Ради того, что все сложные и хорошо оплачиваемые задачи бэкенда возникают именно на границах между процессами: сеть подводит, ответы приходят не в том порядке, транзакция не может накрыть два сервиса. В монолите этих задач просто нет.

## 2. Почему у каждого сервиса своя база (database per service)

Соблазн: одна база на всех, джойны работают, транзакция атомарна. Так делать нельзя, иначе сервисы связаны через схему БД и это монолит с лишними сетевыми вызовами.

Что мы теряем, разделив базы, и чем это компенсируем:

- **Нет JOIN между сервисами.** Данные для карточки товара приходится собирать несколькими вызовами и склеивать в памяти → отсюда паттерн агрегации fan-out/fan-in (этап 2).
- **Нет одной транзакции на всю операцию.** «Списать со склада и провести оплату» атомарно уже невозможно → отсюда саги, outbox, компенсации (этап 3).
- **Данные дублируются.** У заказа хранится название товара на момент покупки, хотя товар живёт в другом сервисе → это нормально и называется денормализацией по границам контекстов.

## 3. Что внутри одного сервиса: слои и правило зависимостей

Дальше в плане это называется «гексагональная архитектура» или «ports and adapters». На пальцах — три круга:

**Домен (ядро).** Сущности и правила: что такое товар, какие у заказа состояния, из какого в какое можно перейти, когда цена невалидна. Здесь нет ни SQL, ни HTTP, ни protobuf. Этот код можно тестировать без запуска чего-либо.

**Сценарии (usecase / application).** «Опубликовать товар», «оформить заказ». Сценарий дёргает домен и просит внешний мир о помощи через **порты** — интерфейсы вроде «хранилище товаров» или «отправитель событий». Сценарий знает *что* нужно («сохрани»), но не знает *чем* (Postgres? файл? мок в тесте?).

**Адаптеры (края).** Реализации портов и точки входа: gRPC-сервер, HTTP-хендлеры, репозиторий на Postgres, клиент Redis, продюсер Kafka.

**Правило зависимостей:** стрелки всегда внутрь. Домен ничего не знает о внешнем; адаптеры знают о домене. Практический критерий: если замена Postgres на что-то другое требует правок в домене — слои размазаны.

**Порт объявляется там, где используется** (в пакете сценариев), а не рядом с реализацией. Это ключевая деталь, из-за которой архитектура работает: сценарий диктует, какой интерфейс ему нужен.

**Не переусложняй.** Интерфейс нужен там, где есть вторая реализация или потребность подменить в тесте. Интерфейс на каждый чих — это карго-культ, и он тоже стоит производительности (см. escape analysis на этапе 4).

## 4. gRPC и Protobuf на пальцах

**Protobuf** — язык описания контракта. В `.proto`-файле ты пишешь: какие есть сообщения (структуры с пронумерованными полями) и какие есть методы (принимает такое-то сообщение, возвращает такое-то). Из этого файла кодогенератор делает Go-структуры и клиент/сервер. Контракт — единственный источник правды, руками сгенерированный код не трогают.

**Почему номера полей важнее имён.** В бинарном формате поле кодируется номером, а не именем. Значит, переименовать поле безопасно, а вот поменять номер или тип — сломать всех клиентов. Отсюда правила совместимости: только добавлять новые поля с новыми номерами, никогда не переиспользовать старые номера, удалять через `reserved`.

**gRPC** — как эти сообщения летают по сети: HTTP/2, бинарно, с постоянным соединением и мультиплексированием запросов в одном соединении. Отсюда два следствия, которые всплывут позже: это быстро и компактно (хорошо), но одно долгоживущее соединение прилипает к одному серверу и ломает наивную балансировку (этап 5).

Что нужно знать про gRPC сверх этого:

- **Виды вызовов.** Нам почти везде хватит unary (запрос-ответ). Стримы — только там, где реально поток (например, выгрузка большого списка), и без фанатизма.
- **Status codes.** У gRPC свой набор кодов (`NotFound`, `InvalidArgument`, `AlreadyExists`, `DeadlineExceeded`, `Unavailable`, `Internal`…). Правильный код — часть контракта: по нему клиент решает, ретраить ли. `Internal` на всё — потеря информации.
- **Metadata.** Аналог заголовков: туда кладутся токен, request-id, trace context.
- **Интерцепторы (interceptors).** То же, что middleware в HTTP: обёртка вокруг каждого вызова. Здесь живёт всё сквозное — логирование, метрики, трейсинг, recover от паники, авторизация, таймауты. Порядок обёрток имеет значение: recover должен быть снаружи, чтобы поймать панику из остальных.

## 5. `context` — нервная система запроса

`context.Context` первым аргументом почти всюду. Он делает три вещи:

1. **Дедлайн.** «Этот запрос не имеет смысла после такого-то момента». Дедлайн распространяется вниз: gateway дал 800 мс — все вложенные вызовы и запросы в БД обязаны уложиться.
2. **Отмена.** Клиент отвалился или сосед вернул ошибку → контекст закрывается, и вся работа под ним должна прекратиться. Драйверы Postgres, Redis, gRPC умеют это уважать, если ты передаёшь им контекст, а не `context.Background()`.
3. **Перенос значений.** request-id, trace context, данные пользователя. Только для сквозных вещей, не для передачи параметров бизнес-логики.

**Главные грабли.** `context.Background()` в середине цепочки обрывает отмену: наверху всё отменилось, а внизу запрос продолжает жить и жрать соединение с базой. Второе: горутина, запущенная в обработчике запроса и не привязанная к контексту, переживает запрос и утекает.

**Бюджет таймаутов** — концепция, которую стоит принять сразу: у входящего запроса есть общий бюджет, каждый уровень отдаёт вниз меньше, чем получил (с запасом на свою работу). Если внутренний таймаут больше внешнего — он бессмысленен, наружу уже вернули ошибку.

## 6. Конкурентность в Go: минимальная модель в голове

**Горутина** — очень дешёвая функция, запущенная параллельно. Дешевизна обманчива: её всё равно нужно кому-то остановить и дождаться.

**Канал** — типизированная очередь для передачи данных между горутинами. Небуферизованный канал — это рандеву (отправитель ждёт получателя). Буферизованный — очередь фиксированной длины, и её длина = сколько ты готов накопить перед тем, как замедлить производителя.

**`select`** — ожидание нескольких событий сразу; почти всегда одна из ветвей — `ctx.Done()`.

Три правила, которые снимают 90% проблем:

1. **Кто запустил горутину, тот отвечает за её остановку.** В момент `go func()` ты должен уже знать, как она узнает, что пора закончиться (контекст, закрытие канала), и кто дождётся её завершения (`sync.WaitGroup`, `errgroup`).
2. **Ограничивай параллелизм.** «Горутина на каждый входящий запрос» = неограниченная нагрузка на БД и память. Инструменты: пул воркеров, семафор (буферизованный канал или `errgroup.SetLimit`).
3. **Общая изменяемая память — только под защитой.** `sync.Mutex` для «читают и пишут примерно одинаково», `sync.RWMutex` когда читателей на порядок больше, атомики для счётчиков. Или вообще без разделяемой памяти — через каналы.

**Гонка данных (data race)** — два потока обращаются к одной памяти без синхронизации, и хотя бы один пишет. В Go это не «редко ломается», а неопределённое поведение, вплоть до порчи структуры map и паники. Детектор гонок (`-race`) — обязательный режим для тестов; он находит только то, что реально выполнилось, поэтому важны тесты, которые действительно дёргают код параллельно.

**Что такое «утечка горутины».** Горутина навсегда заблокирована на отправке в канал, который никто не читает (или на чтении из канала, в который никто не пишет). Она держит память и не умрёт никогда. Симптом — растущее число горутин на графике; ловится профилем `goroutine` (этап 4).

## 7. Транзакции и почему их не хватает

Внутри одной базы у нас есть ACID: либо всё применилось, либо ничего. На этом держится единственная надёжная гарантия во всей системе — **атомарная запись в одну БД**.

Как только операция затрагивает две системы (моя база + Kafka, или мой сервис + чужой сервис), атомарности нет. Классическая ошибка называется **dual write**: записал в базу, потом собрался отправить событие — и упал между этими действиями. Данные есть, события нет; система разъехалась.

Теоретическое решение — распределённая транзакция (2PC, двухфазный коммит). На практике её почти не используют: она требует блокировок на время всего протокола, плохо переживает падение координатора и не поддерживается половиной участников (Kafka, внешние API).

Практические решения, которые мы и будем строить:

- **Transactional Outbox** — событие пишется в ту же базу и в той же транзакции, что бизнес-данные, в отдельную таблицу; отдельный процесс потом дочитывает её и публикует в Kafka. Атомарность сохранена, публикация стала «когда-нибудь, но обязательно».
- **Saga** — длинная операция как последовательность локальных транзакций, у каждой из которых есть **компенсация** (не «откат», а обратное бизнес-действие: не «отменить списание», а «сделать возврат»).
- **Идемпотентность** — свойство операции «повторный вызов не меняет результат». Это фундамент всего асинхронного мира: раз доставка «хотя бы один раз», значит обработка обязана переносить повторы.

Из уровней изоляции достаточно понимать, что при обычном `READ COMMITTED` два конкурентных «прочитал → посчитал → записал» затирают друг друга (lost update), и лечится это либо блокировкой строки, либо условным обновлением, либо версией строки (оптимистичная блокировка).

## 8. Кэш: почему это самая коварная часть

Кэш — копия данных ближе к потребителю. Он даёт скорость и снимает нагрузку с базы, а платишь ты **несогласованностью**: где-то лежит устаревшая версия.

Базовая схема — **cache-aside**: сначала смотрим в кэш, при промахе идём в базу и кладём в кэш с TTL. Альтернативы (write-through, write-behind) сложнее и нужны реже.

Понятия, которые встретятся на этапе 2:

- **TTL** — время жизни записи. Единственный механизм, который спасает от несогласованности «по умолчанию»: даже если ты забыл инвалидировать, через TTL правда вернётся.
- **Инвалидация** — принудительное выбрасывание записи при изменении данных. Правило: **удалять, а не перезаписывать** (перезапись легко затирает более свежее значение из параллельного запроса).
- **Cache stampede / thundering herd** — ключ истёк, и сто параллельных запросов одновременно побежали в базу за одним и тем же. Лечится дедупликацией запросов в процессе (`singleflight`), распределённым замком, разбросом TTL (jitter) и обновлением до истечения.
- **Hot key** — один ключ собирает непропорциональную долю трафика (товар с распродажи). Лечится локальным кэшем перед Redis.
- **L1/L2** — двухуровневый кэш: L1 в памяти процесса (наносекунды, но у каждой реплики свой и они расходятся), L2 в Redis (общий, но сетевой вызов).
- **Negative caching** — кэшировать и факт «такого нет», иначе запросы к несуществующим ключам всегда бьют в базу.

## 9. Брокер сообщений (Kafka) на пальцах

**Топик** — именованный поток событий. **Партиция** — часть топика; порядок гарантирован **только внутри партиции**. Ключ сообщения определяет партицию: одинаковый ключ → та же партиция → сохранённый порядок. Поэтому «все события одного заказа с ключом `order_id`» — это не деталь, а требование корректности.

**Оффсет** — позиция читателя в партиции. **Consumer group** — группа читателей, между которыми партиции распределяются; в группе одну партицию читает ровно один консьюмер. Отсюда: больше консьюмеров, чем партиций — лишние простаивают.

**Rebalance** — перераспределение партиций при появлении/исчезновении консьюмера. Во время него обработка останавливается, а если ты обрабатывал сообщение слишком долго — брокер решит, что ты умер, и отдаст твою партицию другому. Так рождаются дубликаты.

**Гарантии доставки.** На практике у нас **at-least-once**: сообщение может прийти дважды. «Ровно один раз» в распределённой системе достигается не транспортом, а идемпотентной обработкой на стороне получателя (таблица обработанных сообщений или естественная идемпотентность операции).

**DLQ (dead letter queue)** — топик для сообщений, которые не удалось обработать после N попыток. Без него один «отравленный» месседж останавливает всю партицию навсегда.

**Consumer lag** — насколько читатель отстал от конца партиции. Главная метрика здоровья асинхронной части.

## 10. Observability: три сигнала

- **Логи** — «что именно случилось с этим запросом». Обязательно структурные (набор полей, а не строка), обязательно с request-id и trace-id, без персональных данных и секретов.
- **Метрики** — «как система чувствует себя в целом»: числа во времени, дешёвые, агрегированные. Не годятся для поиска конкретного случая (нельзя лепить в метки ID пользователя — это убьёт Prometheus).
- **Трейсы** — «где ушло время в одном запросе через пять сервисов». Запрос = **trace**, каждый шаг = **span**, спаны вложены. Ключевая механика — **propagation**: идентификатор трейса едет в gRPC-метаданных и в заголовках Kafka-сообщений; забыл пробросить — трейс обрывается.

Практические рамки: **RED** для сервисов (Rate, Errors, Duration), **USE** для ресурсов (Utilization, Saturation, Errors). **SLO** — обещание («99% чтений карточки быстрее 200 мс»), **error budget** — сколько нарушений допустимо, и алерт лучше строить на скорости прожигания бюджета, а не на «ошибка случилась».

## 11. Docker и Kubernetes: минимум понятий

**Образ** — неизменяемый шаблон (наши бинарник + сертификаты, ничего лишнего). **Контейнер** — запущенный экземпляр. Многоступенчатая сборка нужна, чтобы в финальный образ не попал компилятор и исходники.

Kubernetes — декларативный: ты описываешь *желаемое состояние*, контроллеры бесконечно приводят реальность к нему (reconcile loop). Отсюда: чинить прод руками через `kubectl edit` бессмысленно — состояние вернётся к описанному.

Объекты, которые нужны:

- **Pod** — минимальная единица запуска (один или несколько контейнеров). Одноразовый: умер — создаётся новый, с новым IP.
- **Deployment** — «хочу N экземпляров такой-то версии», умеет rolling update.
- **Service** — стабильное имя и виртуальный IP перед меняющимся набором подов. Балансирует на уровне соединений (не запросов!) — вот откуда проблема с gRPC.
- **Ingress** — вход снаружи в кластер.
- **ConfigMap / Secret** — конфиги и секреты отдельно от образа.
- **Probes** — три разных вопроса к контейнеру: `startup` («уже запустился?»), `readiness` («можно давать трафик?»), `liveness` («не завис ли насмерть, надо ли перезапускать?»). Путать их — самая частая причина самодельных аварий.
- **requests / limits** — сколько ресурсов гарантировано и сколько максимум. Превысил лимит памяти → OOMKill; превысил CPU → троттлинг (не убийство, но очень больно, см. этап 4).

## 12. Рабочий инструментарий и цикл разработки

- **Монорепа.** Один репозиторий: `proto/` (контракты), `services/<name>/` (по сервису на папку: `cmd/`, `internal/domain`, `internal/usecase`, `internal/adapter/...`), `pkg/` (общее, но осторожно — общий код связывает сервисы), `deploy/` (compose, helm-чарты), `docs/` (план, ADR, диаграммы).
- **Единая точка команд.** `Taskfile`/`Makefile`: `gen`, `lint`, `test`, `up`, `migrate`, `load`. Всё, что делается руками дважды, переезжает сюда.
- **CI с первого дня.** Сборка + линтер + тесты с `-race` + проверка совместимости протофайлов. Даже если проект в одиночку: CI — это тренировка дисциплины и страховка от «работает на моей машине».
- **Тесты.** Юнит на домен (быстро, без инфраструктуры). Интеграционные на реальных Postgres/Redis/Kafka в контейнерах (медленнее, но проверяют то, что реально ломается: SQL, транзакции, сериализацию). Моки — только для внешних API.
- **ADR** — короткая заметка на каждое неочевидное решение: контекст, варианты, выбор, цена. Пиши в момент решения, не потом.

## 13. Глоссарий одной строкой

- **Идемпотентность** — повтор операции не меняет результат.
- **Порт / адаптер** — интерфейс, объявленный сценарием / его конкретная реализация.
- **Интерцептор / middleware** — обёртка вокруг каждого вызова для сквозной логики.
- **Fan-out / fan-in** — разослать N параллельных запросов / собрать N ответов в один.
- **Worker pool** — фиксированное число горутин, разбирающих задачи из очереди.
- **Backpressure** — замедление источника, когда потребитель не успевает.
- **Graceful shutdown** — завершение без потери обрабатываемых запросов.
- **Cache-aside** — читаем кэш, при промахе — базу и заполняем кэш.
- **Stampede** — лавина одновременных промахов по одному ключу.
- **Outbox** — таблица событий, пишущаяся в транзакции с данными.
- **CDC** — чтение изменений напрямую из журнала БД (WAL).
- **Saga** — цепочка локальных транзакций с компенсациями.
- **Компенсация** — обратное бизнес-действие вместо отката.
- **CQRS** — раздельные модели для записи и чтения.
- **Eventual consistency** — согласованность «через некоторое время».
- **Span / trace** — шаг / полный путь запроса в трассировке.
- **Cardinality** — число уникальных комбинаций меток метрики.
- **Escape analysis** — решение компилятора, где жить переменной: стек или куча.
- **Circuit breaker** — предохранитель, отсекающий вызовы к упавшей зависимости.
- **Bulkhead** — изоляция ресурсов, чтобы одна зависимость не съела все.
- **Load shedding** — осознанный отказ части запросов ради выживания системы.
- **Expand-contract** — миграция схемы в два шага для совместимости версий.
- **GitOps** — желаемое состояние кластера описано в git, агент его применяет.
