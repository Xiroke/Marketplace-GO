# Этап 1. Скелет и контракты: три процесса, которые не теряют запросы

**Срок:** 3–4 недели. **Предусловие:** прочитан `00-fundamentals.md`.

## Зачем этот этап

Ты один раз выстраиваешь «эталонный сервис» и потом копируешь его шесть раз. Всё, что здесь сделано криво, будет умножено на восемь: криво сделанные ошибки, конфиги, логи и завершение работы придётся переделывать во всех сервисах сразу. Поэтому этап не про фичи, а про шаблон.

Второй смысл: к концу этапа у тебя есть работающая система из трёх процессов, которую можно поднять одной командой. Это психологически важно — дальше ты улучшаешь работающее, а не строишь с нуля.

## Что должно работать в конце (демо-сценарий)

1. Поднял всё одной командой; поднялись gateway, identity, catalog, два Postgres, MinIO.
2. Зарегистрировался, залогинился, получил пару токенов.
3. С токеном продавца создал товар, загрузил картинку, опубликовал.
4. Без токена получил публичный список товаров с фильтром и постраничной навигацией.
5. Запросил чужой товар на редактирование — получил корректную 403, а не 500.
6. Во время потока запросов остановил сервис штатным сигналом — ни один уже принятый запрос не оборвался, а новые сразу получили отказ.

## Ключевые концепции этапа

**Contract-first.** Сначала `.proto`, потом код. Контракт — это то, что видят другие сервисы; он должен быть спроектирован, а не «получиться» из кода.

**Единая модель ошибок.** У тебя три представления одной ошибки: доменная (внутри Go), gRPC status (между сервисами), HTTP-ответ (наружу). Нужны два явных места перевода. Доменные ошибки — типизированные (не строки), помечены категорией: «не найдено», «неверный ввод», «конфликт», «нет прав», «внутренняя». Наружу отдаётся стабильный конверт: машинный код ошибки, человеческое сообщение, request-id для поддержки. Внутренние детали (текст ошибки SQL) наружу не уходят никогда.

**Конфиг и fail fast.** Всё из переменных окружения, разбор на старте, при отсутствии обязательного значения — падаем сразу с понятным сообщением, а не через час на первом запросе. Секреты никогда не логируются.

**Keyset-пагинация.** `OFFSET 10000` заставляет БД пролистать 10000 строк и ломается, когда данные меняются между страницами. Правильно — «дай N записей после вот этого курсора», где курсор строится из полей сортировки и уникального ключа. Это заметно и на интервью: вопрос про пагинацию любят.

**Graceful shutdown как протокол.** Приходит `SIGTERM`. Дальше строго по шагам: (1) переключаем readiness в «не готов», чтобы перестали приходить новые запросы; (2) ждём небольшую паузу, пока балансировщик это заметит; (3) закрываем приём новых соединений, но даём текущим доработать до дедлайна; (4) останавливаем фоновые задачи через контекст и дожидаемся их `WaitGroup`; (5) закрываем пул БД, Redis, продюсеры; (6) выходим с кодом 0. Порядок обратный порядку запуска. На всё есть общий дедлайн, по истечении — выходим принудительно, иначе платформа убьёт процесс жёстко.

## Маршрут

### Шаг 1. Репозиторий и инструментарий (2–3 дня)

Заведи монорепу с раскладкой из `00-fundamentals.md` §12. Настрой сразу: `golangci-lint` с осмысленным набором линтеров, `Taskfile`, `.editorconfig`, CI (сборка, линт, тесты с `-race`). Заведи `docs/adr/` и `docs/journal.md`.

Ощущение «это трата времени» обманчиво: настроенный на пустом проекте CI занимает час, на проекте из восьми сервисов — день.

### Шаг 2. Контракты (2–3 дня)

Опиши protobuf-контракты для `identity` и `catalog`. Решения, которые надо принять осознанно (и записать в ADR):

- Структура директорий и версий: пространство имён вида «продукт / сервис / версия», версия в пути — чтобы `v2` мог сосуществовать с `v1`.
- Отдельные типы для запроса/ответа на каждый метод (не переиспользовать одно сообщение в двух методах — иначе поля начнут расползаться).
- Внутреннее и внешнее представление: одно и то же сообщение не должно обслуживать и публичный API, и внутренние нужды (у продавца и покупателя разный набор полей товара).
- Как выражать «поле не передано» против «поле сброшено в ноль» — это про optional-семантику и про частичное обновление (маска полей).
- Деньги: никогда не число с плавающей точкой. Целое число минимальных единиц + код валюты.
- Время: единый тип времени и UTC везде.

Настрой линтер протофайлов и проверку обратной совместимости в CI. Сломай контракт специально (поменяй номер поля) и убедись, что CI это ловит.

### Шаг 3. Сервис `identity` (4–5 дней)

Домен: пользователь, учётные данные, роли. Пароль хранится только как хеш современным алгоритмом с солью и подобранной стоимостью — и здесь же первый компромисс: дорогой хеш даёт нагрузку на CPU при логине (вернёмся к этому на этапе 4).

Токены: короткоживущий access и долгоживущий refresh. Ключевые решения:

- **Как остальные сервисы проверяют токен?** Вариант А: дёргают `identity` по gRPC на каждый запрос (просто, но это единая точка отказа и лишняя задержка). Вариант Б: подпись асимметричным ключом, публичный ключ раздаётся и кэшируется, проверка локальная (быстро, но отзыв токена становится сложным). Выбери, обоснуй, запиши. Обычно в реальности: локальная проверка + короткий TTL access-токена.
- **Ротация refresh-токенов** и обнаружение повторного использования (если старый refresh пришёл дважды — вероятно, украли, надо инвалидировать всю цепочку). Здесь ты впервые столкнёшься с необходимостью хранить состояние сессий.
- **Где живёт авторизация?** Аутентификация («кто ты») — в gateway. Авторизация («можно ли тебе это») — частично в gateway (грубо, по роли), но проверка «этот товар принадлежит этому продавцу» обязана быть в `catalog`, потому что только он знает владельца. Не отдавай решения о правах наружу.

### Шаг 4. Сервис `catalog` (5–6 дней)

Домен: товар (владелец, название, описание, цена, категория, атрибуты, статус), категория (дерево), статусы `draft → published → archived` с явно разрешёнными переходами. Сразу заложи мягкое удаление и `created_at/updated_at`.

Работа с БД:

- Миграции — файлами, вперёд и назад, с первого дня. Ни одной ручной правки схемы.
- Запросы — типизированной генерацией из SQL (видно план запроса, нет магии ORM). Это осознанный отказ от ORM: на этом проекте важнее понимать SQL.
- Дерево категорий: сравни варианты (родительская ссылка с рекурсивным запросом, materialized path, ltree) и выбери. Это хорошая маленькая задача по проектированию.
- Индексы под фактические запросы листинга. Загляни в план запроса — привыкай смотреть его до того, как «стало медленно».
- Транзакции наружу из репозитория не текут: сценарий говорит «выполни это как одну транзакцию», а как это устроено — деталь адаптера.

### Шаг 5. `api-gateway` (4–5 дней)

Роутер на Chi, цепочка middleware в осмысленном порядке: восстановление после паники → request-id → логирование → метрики → CORS → таймаут → аутентификация → ограничение размера тела. Дальше:

- Валидация входа на границе. Домен доверяет данным, потому что их проверили на входе.
- Явный маппинг DTO ↔ protobuf. Соблазн отдавать protobuf-структуры наружу как JSON надо задавить: внешний контракт начнёт зависеть от внутреннего.
- gRPC-клиенты создаются один раз на старте (одно соединение переиспользуется), а не на каждый запрос.
- Бюджет таймаутов: пришёл HTTP-запрос → назначили общий дедлайн → каждый gRPC-вызов получает свою часть.
- OpenAPI-описание внешнего API. Можно генерировать, можно писать руками, но оно должно быть.

### Шаг 6. Сквозная обвязка (3–4 дня)

Оформи как переиспользуемые пакеты (это войдёт во все следующие сервисы): загрузка конфига, структурный логгер с полями из контекста, health-эндпоинты (`/healthz` — жив, `/readyz` — готов, с проверкой критичных зависимостей), эндпоинт с версией и хешем сборки, набор gRPC-интерцепторов, graceful shutdown по протоколу выше.

Здесь же — заготовка на будущее: базовые метрики и трейсинг лучше подключить уже сейчас, минимальным объёмом. Тогда этапы 2 и 3 ты будешь проходить с приборами, а не на ощупь.

### Шаг 7. Docker и локальный запуск (2–3 дня)

Многоступенчатая сборка, финальный образ минимальный и без root, без исходников и компилятора. Compose-файл: сервисы, две базы, MinIO, healthcheck'и и зависимости по готовности (а не по факту запуска). Отдельно продумай, как накатываются миграции при старте — и заметь для себя, что при нескольких репликах этот вопрос станет проблемой (этап 5).

### Шаг 8. Тесты (параллельно, 3–4 дня суммарно)

- Юнит-тесты домена: переходы статусов, валидация, расчёт цены. Табличные, без инфраструктуры.
- Интеграционные: реальный Postgres в контейнере, проверка репозиториев, транзакций, миграций «вперёд-назад». Каждый тест получает чистое состояние.
- Один сквозной тест на gateway: регистрация → создание товара → чтение списка.

## Эксперименты (это и есть обучение)

1. **Дедлайн.** Поставь искусственную задержку в `catalog`, а на gateway — таймаут меньше задержки. Проверь по логам, что запрос в Postgres реально прервался, а не доработал в пустоту. Потом сделай в одном месте `context.Background()` и посмотри, как отмена перестаёт работать.
2. **Пул соединений.** Выставь пул в 50 и запусти 5 экземпляров сервиса против базы с лимитом 100 соединений. Получи «too many connections». Затем посчитай арифметику и почитай, зачем нужен PgBouncer.
3. **Graceful shutdown.** Пусти постоянный поток запросов и пошли `SIGTERM`. Сначала без graceful (мгновенный выход) — посчитай оборванные. Потом с graceful. Разница в числах — то, что ты будешь рассказывать на интервью.
4. **Паника.** Сделай сознательное разыменование nil в хендлере. Без интерцептора recover упадёт весь процесс со всеми параллельными запросами; с ним — только один запрос получит `Internal`.

## Ловушки этапа

**1. Контекст без дедлайна и «зомби-запросы».**
Механика: gateway принял запрос, клиент отключился, но никто не выставил дедлайн. gRPC-вызов, а за ним запрос в Postgres продолжают выполняться и держать соединение из пула. Под нагрузкой пул выедается мёртвой работой, и сервис встаёт, хотя «ничего не делает».
Лечение: обязательный дедлайн на входе, убывающий бюджет вниз по стеку, передача `ctx` во все вызовы БД, различение `context.Canceled` (клиент ушёл — это не ошибка сервиса, не должно попадать в метрику 5xx) и `DeadlineExceeded`.

**2. Арифметика пула соединений.**
Механика: размер пула умножается на число реплик. Postgres по умолчанию не готов к сотням соединений: каждое — процесс со своей памятью, и после определённого предела рост параллелизма *снижает* пропускную способность.
Лечение: считать `реплики × пул + фоновые задачи + миграции ≤ лимит базы` с запасом; ограничивать время жизни соединения; понимать, зачем внешний пулер. Здесь же поймёшь, почему «просто добавь реплик» не всегда работает.

**3. Graceful shutdown, который не graceful.**
Механика: платформа посылает `SIGTERM` и одновременно исключает под из балансировки — но не мгновенно, эти события асинхронны. Если ты закрываешь сервер сразу, часть уже отправленного трафика получает разорванное соединение. Симптом — редкие ошибки у клиентов ровно во время деплоя, которые никто не связывает с деплоем.
Лечение: сначала снять readiness, потом короткая пауза, только потом закрытие; согласовать общий дедлайн завершения с настройками платформы (этап 5); не забыть про фоновые горутины — их тоже надо дожидаться.

**4. Бонус: ошибки, потерявшие смысл.**
Механика: домен возвращает `errors.New("not found")`, адаптер оборачивает в `Internal`, клиент получает 500 и ретраит то, что ретраить бессмысленно. Ретраи на неретраибельные ошибки — прямой путь к перегрузке (этап 5).
Лечение: типизированные доменные ошибки, единая таблица соответствия «доменная категория → gRPC код → HTTP статус», обёртка ошибок с сохранением причины.

**5. Бонус: контракт, который сломался незаметно.**
Механика: поменял тип поля или переиспользовал номер — старый клиент читает мусор без ошибки десериализации. Ошибка проявится как «странные данные», а не как отказ.
Лечение: правила совместимости + автоматическая проверка в CI, `reserved` для удалённых номеров.

## Definition of Done

- [ ] `task up` поднимает всю систему; демо-сценарий проходит целиком.
- [ ] Контракты линтуются, совместимость проверяется в CI.
- [ ] Ошибки: единый конверт наружу, корректные gRPC-коды, внутренние детали не утекают.
- [ ] Логи структурные, у каждой записи есть request-id; секретов в логах нет.
- [ ] Graceful shutdown измерен: потерянных запросов при остановке — ноль.
- [ ] Интеграционные тесты на реальном Postgres, миграции откатываются.
- [ ] CI зелёный, `-race` включён.
- [ ] ADR: способ проверки токенов, представление денег, пагинация, дерево категорий.
- [ ] Все пять ловушек воспроизведены и описаны в дневнике.
