# Этап 5. Kubernetes и устойчивость: выжить под нагрузкой и при отказах

**Срок:** 4 недели. **Предусловие:** этапы 1–4 закрыты (особенно четвёртый — без приборов этот этап бессмысленен).

## Зачем этот этап

До сих пор всё жило в Compose, где сеть надёжна, а процессы не переезжают. Kubernetes добавляет главную особенность продакшена: **всё постоянно меняется само**. Поды пересоздаются, IP-адреса меняются, соединения рвутся, реплик становится больше и меньше. Код, который это не учитывает, работает локально и сыпется в кластере.

Второй смысл этапа — устойчивость как проектное свойство. Отказ одной зависимости не должен превращаться в отказ системы. Это набор конкретных паттернов, и их надо не просто прикрутить, а увидеть в работе на своих графиках.

## Что должно работать в конце (демо-сценарий)

1. Весь стек поднимается в локальном кластере из описаний в git, без ручных команд; откат на предыдущую версию — одно действие.
2. Rolling update во время потока запросов: ни одного потерянного запроса, ни одного 5xx.
3. Десять реплик сервиса каталога реально делят нагрузку (видно по per-pod метрикам), а не одна тащит всё.
4. Сервис оплаты полностью недоступен: каталог и карточка работают, оформление заказа отказывает быстро и внятно, лавины ретраев нет.
5. Всплеск нагрузки ×5: реплики добавляются автоматически по осмысленной метрике; консьюмеры масштабируются по лагу.
6. Миграция схемы с переименованием поля прокатывается без простоя при разных версиях кода в кластере одновременно.
7. Chaos-день: убийство пода, брокера, primary базы, искусственная задержка сети — на каждый случай есть запись «гипотеза → что увидел → вывод → фикс».

## Ключевые концепции этапа

**Декларативность и цикл согласования.** Ты описываешь желаемое состояние; контроллеры непрерывно приводят реальность к описанию. Практическое следствие: ручные правки в кластере обречены — они либо будут перезаписаны, либо создадут расхождение с git, которое потом никто не сможет объяснить. Отсюда GitOps: git — единственный источник правды, агент в кластере применяет и сообщает о расхождениях.

**Три пробы — три разных вопроса.** `startup`: «процесс ещё поднимается, не трогайте» (нужна там, где долгий старт: миграции, разогрев кэша). `readiness`: «можно ли давать трафик прямо сейчас» — переключается туда-обратно много раз за жизнь пода, и её отрицательный ответ просто убирает под из балансировки. `liveness`: «процесс завис насмерть, надо перезапустить» — её отрицательный ответ убивает контейнер. Самая частая рукотворная авария в отрасли: положить проверку зависимостей (базы, брокера) в liveness. База моргнула → все поды признаны мёртвыми → все перезапустились → connection storm → база легла окончательно.

**Requests и limits.** Requests — это то, по чему планировщик выбирает узел и что тебе гарантировано. Limits — жёсткий потолок: по памяти его превышение означает мгновенное убийство контейнера, по CPU — принудительное замедление (см. этап 4). Правило для сервиса с требованиями по задержке: память просить и ограничивать примерно одинаково (иначе непредсказуемо), CPU — просить по реальному потреблению, а лимит ставить осознанно, понимая, что он вводит троттлинг.

**Жизненный цикл завершения пода.** Момент удаления пода порождает два параллельных процесса: сигнал контейнеру и исключение пода из списка получателей трафика. Они **не синхронизированы**, и второй занимает время. Отсюда: обработчик до остановки с небольшой паузой, снятие readiness первым делом, и общий срок завершения, согласованный с дедлайном graceful shutdown из этапа 1 (срок в манифесте должен быть больше внутреннего дедлайна, иначе тебя добьют посреди дренажа).

**Почему gRPC не балансируется сам.** Обычный Service балансирует **соединения**, а не запросы. gRPC держит одно долгоживущее соединение и мультиплексирует в нём все запросы. Итого: клиент один раз выбрал под и стучит только в него до конца жизни соединения. Масштабирование не работает, при этом никакой ошибки нет — только перекошенные графики. Решения: клиентская балансировка (обнаружение всех адресов через headless-сервис и распределение запросов по подключениям ко всем подам), ограничение максимального возраста соединения на сервере (чтобы состав пересматривался при изменении числа реплик), либо прокси/сервис-меш, который умеет балансировать HTTP/2 по запросам.

**Паттерны устойчивости.**
*Бюджет таймаутов* — сверху вниз, каждый уровень оставляет себе запас; внутренний таймаут больше внешнего бессмыслен.
*Ретраи* — только для идемпотентных операций, только на «повторяемые» коды, с экспоненциальной задержкой **и разбросом**, с ограничением общей доли повторов от трафика. Без разброса повторы синхронизируются и бьют залпами.
*Circuit breaker* — предохранитель: после серии отказов перестаёт даже пытаться (мгновенный отказ вместо ожидания таймаута), периодически пропускает пробный запрос. Смысл двойной: не мучить упавшую зависимость и не держать свои горутины и соединения в ожидании.
*Bulkhead* — раздельные ограничения на каждую зависимость, чтобы медленная зависимость не съела весь пул исполнения и не утащила за собой независимые эндпоинты.
*Load shedding* — при перегрузке отказывать части запросов быстро и осознанно, по приоритету (оформление заказа важнее пересчёта рекомендаций). Ключевая мысль: система, которая честно отказывает в 20% запросов, работоспособна; система, которая всем отвечает по 30 секунд, мертва.
*Rate limiting* — защита от одного шумного клиента. Локально (на реплику) просто, но при N репликах фактический лимит умножается; распределённый на Redis точнее, но добавляет сетевой вызов и зависимость на горячем пути.

**Каскадный отказ.** Схема одна и та же: зависимость замедлилась → у клиентов растёт число ожидающих запросов → кончаются пулы и память → клиент сам становится медленным → его клиенты начинают ретраить → нагрузка на упавшую зависимость выросла в разы именно тогда, когда ей нужно восстановиться. Всё, что перечислено выше, существует ради разрыва этой цепочки.

**Миграции без простоя (expand-contract).** Во время rolling update в кластере одновременно живут две версии кода, значит схема должна быть совместима с обеими. Отсюда три шага, разнесённые по релизам: сначала расширить (добавить новое, писать в оба места, читать из старого), потом переключить чтение и перелить данные, и только в следующем релизе убрать старое. Любое одношаговое переименование или удаление колонки = гарантированный простой.

**Chaos engineering.** Не «ломать ради веселья», а проверять гипотезы: «если умрёт брокер, оформление заказов будет отклоняться с внятной ошибкой, а чтение каталога не пострадает». Ставишь гипотезу, ломаешь, сравниваешь с фактом. Расхождение между ожиданием и фактом — самая ценная информация на всём этапе.

## Маршрут

### Шаг 1. Кластер и первый сервис (3–4 дня)

Локальный кластер (k3d или minikube), отдельное пространство имён. Начни с сырых манифестов для одного сервиса — важно понимать, что генерируют шаблоны. Разберись, как попасть в сервис снаружи, как посмотреть логи, события и причины перезапусков.

### Шаг 2. Инфраструктура в кластере (3–4 дня)

Postgres, Redis, Kafka, ClickHouse, Temporal, Jaeger, Prometheus, Grafana. Готовые чарты или операторы — здесь не нужно героизма, задача не в этом. Что нужно понять: постоянные тома и что происходит с данными при пересоздании пода; почему база в кластере на одном узле — это учебная конфигурация; как хранить секреты вне git (шифрованные секреты или внешний менеджер) и почему пароль в `values.yaml` — это инцидент.

### Шаг 3. Helm и шаблон деплоя (4–5 дней)

Все восемь сервисов деплоятся одним шаблоном с разными значениями. Внутри: пробы, ресурсы, конфиг из ConfigMap/Secret, аннотации для сбора метрик, стратегия обновления, срок завершения, обработчик до остановки, бюджет недоступности при обслуживании узлов.

Отдельно продумай миграции: отдельная задача перед релизом или инициализирующий контейнер? Второй вариант при трёх репликах запустит миграцию трижды параллельно — нужна блокировка на уровне БД. Это хороший маленький ADR.

Никаких плавающих тегов образов: версия образа = конкретная неизменяемая версия, иначе перезапуск пода может тихо поднять другой код.

### Шаг 4. GitOps (2–3 дня)

Поставь ArgoCD, положи описания в git, включи автоматическую синхронизацию. Проверь три вещи: развёртывание из нуля, откат на предыдущую версию, обнаружение расхождения (поменяй что-то руками в кластере и посмотри, что произойдёт). Пойми, чем это отличается от «пайплайн делает apply» и почему разделение сборки и доставки удобно.

### Шаг 5. Балансировка gRPC (3–4 дня)

Сначала воспроизведи проблему: 10 реплик, нагрузка, per-pod метрики из этапа 4 — увидишь перекос. Затем починить: обнаружение всех адресов через headless-сервис плюс распределение на стороне клиента, настройки поддержания соединения и ограничение его максимального возраста. Замерь распределение снова.

Дополнительно (сильный пункт в резюме): поставь Linkerd, получи балансировку по запросам, взаимный TLS между сервисами и метрики «золотых сигналов» без правки кода. Сравни оба подхода в ADR: что дал меш, чем заплатил (лишний прокси в каждом поде, задержка, ещё один компонент для отладки).

### Шаг 6. Устойчивость в коде (5–6 дней)

Здесь ты возвращаешься в Go и вкручиваешь паттерны в клиентов и gateway:

- Бюджет таймаутов сверху вниз, ревизия всех текущих значений (наверняка найдёшь несогласованные).
- Ретраи с разбросом и ограничением доли повторов — только там, где операция идемпотентна. Пройди по всем вызовам и явно отметь, какие можно повторять, а какие нет; это упражнение важнее самого кода.
- Предохранитель на каждый исходящий вызов, с метриками состояния (переходы предохранителя должны быть видны на дашборде).
- Изолированные ограничения параллелизма на каждую зависимость.
- Ограничение частоты запросов на gateway: по клиенту и по эндпоинту, с корректными заголовками ответа. Сделай локальный вариант, замерь фактический лимит при N репликах, потом сделай распределённый и сравни.
- Сброс нагрузки при перегрузке: очередь ожидания ограничена, при переполнении — быстрый отказ; приоритеты эндпоинтов.

### Шаг 7. Автомасштабирование (3–4 дня)

Сначала по CPU — и сразу пойми, почему для сервиса, который ждёт ввода-вывода, это плохая метрика. Затем по прикладным метрикам из Prometheus: запросы в секунду на реплику для сервисов, лаг консьюмера для обработчиков событий. Проверь поведение при резком всплеске: сколько времени занимает реакция, что происходит с новыми подами (холодный кэш! — привет, этап 2), не начинает ли масштабирование колебаться.

Отдельно подумай о нижней границе: масштабирование до нуля для консьюмеров звучит красиво, но первый заказ будет ждать подъёма.

### Шаг 8. Миграция без простоя (2–3 дня)

Возьми реальное изменение (переименовать поле, разделить одно поле на два) и проведи его по схеме «расширить → переключить → убрать» через три релиза, с нагрузкой во время каждого. Для контраста сделай сначала «в лоб» и посмотри на ошибки во время раскатки — это лучший аргумент в пользу схемы.

### Шаг 9. Chaos-день (3–4 дня)

Список экспериментов, каждый с гипотезой, записанной **до** запуска:

1. Убить случайный под сервиса под нагрузкой. Ожидание: единичные ошибки или ноль ошибок, восстановление автоматически.
2. Убить все поды сервиса оплаты. Ожидание: заказы отклоняются быстро, каталог не затронут, предохранитель открыт, ретраи не растут лавиной.
3. Добавить 500 мс задержки к сети до каталога. Ожидание: срабатывают таймауты, деградация карточки, не растёт число горутин.
4. Убить брокер. Ожидание: публикация складывается в outbox и не теряется, после подъёма всё догоняется; лаг виден на графике.
5. Убить базу каталога. Ожидание: чтение частично работает из кэша, запись отказывает, readiness сервиса уходит в «не готов», liveness **не** перезапускает поды.
6. Отобрать CPU (жёсткий лимит) под нагрузкой. Ожидание: рост задержки и троттлинга, но не отказ; масштабирование реагирует.
7. Заполнить диск под Kafka или БД. Ожидание: понятная ошибка и алерт, а не тихая порча.

На каждый эксперимент — короткий runbook: как выглядит симптом на дашборде, что проверить, что сделать. Это и есть тот артефакт, который на интервью выделяет тебя из всех.

## Ловушки этапа

**1. gRPC-соединение прилипло к одному поду.**
Механика: балансировка на уровне соединений плюс долгоживущее HTTP/2-соединение = вся нагрузка идёт в один под. Особенно коварно после масштабирования: добавил реплик, новые поды пустые, старый перегружен. Ошибок нет, только странная задержка.
Лечение: клиентская балансировка через обнаружение всех адресов, ограничение максимального возраста соединения, либо меш. Обнаруживается только per-pod метриками — вот зачем нужен был этап 4.

**2. Пробы, которые сами создают аварию.**
Механика: liveness проверяет доступность базы → база на секунду недоступна → платформа убивает все поды → на старте все ломятся подключаться → connection storm добивает базу → цикл повторяется. Вариант помягче: liveness с коротким таймаутом при пиковой нагрузке считает медленный, но живой сервис мёртвым — и перезапускает его в самый неподходящий момент, усиливая перегрузку. Ещё вариант: readiness мигает при каждой мелочи, и балансировщик постоянно перекраивает состав.
Лечение: liveness проверяет только «процесс не завис» и никогда зависимости; readiness — критичные зависимости, с гистерезисом и разумными порогами; отдельная startup-проба вместо завышенных задержек в liveness.

**3. Лавина повторов (retry storm).**
Механика: зависимость замедлилась → каждый клиент повторяет 3 раза → нагрузка на неё выросла втрое ровно в момент, когда ей плохо → она падает окончательно. Умножается на число уровней: три уровня по три попытки — это 27-кратное усиление.
Лечение: повторы только на одном уровне (обычно ближайшем к зависимости), обязательный разброс задержек, ограничение доли повторов в общем трафике, предохранитель, соблюдение дедлайна (истёк бюджет — не повторять), и на стороне сервиса — сброс нагрузки, чтобы отказывать дёшево.

**4. Миграция, ломающая раскатку.**
Механика: удалил или переименовал колонку → старые поды, которые ещё живут и обслуживают трафик, падают на каждом запросе. Обратный вариант: код требует новую колонку, а миграция ещё не прошла. И третий: миграция запустилась в трёх репликах параллельно и оставила схему в неопределённом состоянии.
Лечение: строго expand-contract в три релиза; блокировка на выполнение миграций; правило «код должен работать и до, и после миграции»; для долгих операций (создание индекса на большой таблице) — неблокирующие варианты и понимание, что миграция может занять часы.

**5. Бонус: connection storm и «стадный» рестарт.**
Механика: одновременный перезапуск всех подов (обновление, вытеснение с узла, авария) → все разом открывают соединения к базе, прогревают пулы, читают конфиги → база и кэш получают пиковую нагрузку в момент, когда ещё ничего не работает. Плюс холодный кэш: после массового рестарта вся нагрузка идёт в базу.
Лечение: разброс старта и постепенное открытие соединений, ограничение одновременно обновляемых подов, бюджет недоступности, прогрев кэша, защита от лавины из этапа 2 (которая именно здесь спасает по-настоящему).

**6. Бонус: консьюмеры и обновления.**
Механика: каждый деплой консьюмера вызывает перераспределение партиций; при частых деплоях группа больше времени перераспределяется, чем работает. Плюс: если остановка консьюмера не встроена в graceful shutdown, при каждом обновлении часть сообщений обрабатывается повторно.
Лечение: корректный выход из группы при завершении, разумный срок завершения, кооперативная стратегия перераспределения, и осознание, что лаг во время деплоя — нормальное явление, если он рассасывается.

**7. Бонус: расхождение с git и «магия в кластере».**
Механика: кто-то (ты) починил прод руками. Через неделю релиз перезаписывает правку, авария возвращается, причина непонятна.
Лечение: только git как источник правды, автоматическое обнаружение расхождений, отладка через «поменять в git и посмотреть», отношение к ручной правке как к аварийному действию, которое обязательно фиксируется.

## Definition of Done

- [ ] Весь стек развёртывается из git в чистый кластер без ручных шагов; откат работает.
- [ ] Rolling update под нагрузкой: ноль потерянных запросов (измерено, не «на глаз»).
- [ ] Нагрузка равномерно распределяется по репликам gRPC-сервисов (доказано per-pod метриками).
- [ ] Пробы разделены по смыслу; проверено, что падение базы не вызывает перезапуск подов.
- [ ] Таймауты, повторы, предохранители и изоляция ресурсов внедрены; состояния предохранителей видны на дашборде.
- [ ] Ограничение частоты и сброс нагрузки работают; поведение под перегрузкой предсказуемо.
- [ ] Автомасштабирование по прикладной метрике реагирует на всплеск; поведение при холодном старте понято.
- [ ] Миграция с переименованием проведена без простоя по схеме расширить/переключить/убрать.
- [ ] Проведено минимум шесть chaos-экспериментов, на каждый есть гипотеза, наблюдение и runbook.
- [ ] Секретов в git нет.
- [ ] ADR: способ балансировки gRPC (меш или клиентская), запуск миграций, локальный или распределённый лимит, политика повторов.

## Финал проекта

После этапа 5 потрать неделю на «упаковку» — она конвертирует четыре месяца работы в результат:

- **README** с диаграммами: контекст системы, контейнеры/сервисы, поток оформления заказа. Явно перечисли, какие проблемы решены и какими паттернами.
- **Демо-сценарий** на 10 минут: поднять, оформить заказ, убить сервис, показать восстановление, показать трейс и дашборд.
- **Список ADR** как отдельная страница — это твой аргумент «я принимал решения, а не копировал туториалы».
- **Разбор для интервью:** на каждую ловушку из всех пяти этапов заготовь короткую историю по схеме «симптом → как искал → в чём была механика → как починил → чем заплатил». Таких историй у тебя будет около тридцати, и они закрывают почти любой вопрос на секции по бэкенду и системному дизайну.

Дальше, если захочется расширять: полнотекстовый поиск по каталогу (OpenSearch + индексация из потока событий), фичефлаги, мультитенантность, шардирование БД, gRPC-федерация или GraphQL-фасад для мобильного клиента, вынос части нагрузки в отдельные регионы. Но это уже другой проект — этот к тому моменту своё дело сделает.
